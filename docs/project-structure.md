# Структура проекта

## Назначение проекта

Проект `shu` представляет собой микросервисный маркетплейс для продажи и покупки книг.

Система состоит из независимых сервисов:

- `api-gateway` — маршрутизация, проверка JWT и ограничения запросов;
- `auth-service` — учетные записи и аутентификация;
- `catalog-service` — книги, категории, характеристики и остатки;
- `cart-service` — корзины пользователей;
- PostgreSQL — постоянное хранение данных;
- Redis — сессии, блокировка токенов, корзины и кэш.

## Общая схема

```text
                      ┌─────────────────┐
Покупатель / клиент │ API Gateway     │
───────────────────>│ Spring Boot      │
                      └───────┬─────────┘
                              │
         ┌────────────────────┼────────────────────┐
         │                    │                    │
         ▼                    ▼                    ▼
┌────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│ Auth Service   │  │ Catalog Service │  │ Cart Service    │
│ Java / JWT     │  │ Python / REST   │  │ Python / Redis  │
└───────┬────────┘  └────────┬────────┘  └────────┬────────┘
        │                    │                    │
        ▼                    ▼                    ▼
  Auth PostgreSQL      Catalog PostgreSQL     Cart PostgreSQL
                                             или Redis
```

Внешний пользователь не обращается напрямую к внутренним сервисам. Все HTTP-запросы проходят через API Gateway.

### contracts

Содержит описания внешних API и форматы событий.

```text
contracts/
├── auth/
│   └── openapi.yaml
├── cart/
│   └── openapi.yaml
├── catalog/
│   └── openapi.yaml
└── events/
    └── order-created.json
```

Назначение файлов:

- `auth/openapi.yaml` — регистрация, вход, refresh и logout;
- `catalog/openapi.yaml` — каталог, товары, поиск и модерация;
- `cart/openapi.yaml` — получение и изменение корзины;
- `order-created.json` — формат события оформления заказа.

Контракты являются основой согласования API и должны обновляться до изменения реализаций сервисов.

## API Gateway

api-gateway

Единая точка входа в систему.

Ответственность:

- прием внешних HTTP-запросов;
- маршрутизация запросов;
- проверка JWT-подписи публичным RSA-ключом;
- проверка отозванных access-токенов в Redis;
- ограничение частоты запросов;
- проброс идентификатора пользователя и роли;
- обработка недоступности микросервисов;
- circuit breaker и тайм-ауты.

Маршруты:

```text
/auth/**     → auth-service
/catalog/**  → catalog-service
/cart/**     → cart-service
```

Публичные и защищенные маршруты должны быть явно перечислены в конфигурации.

Перед forwarding API Gateway добавляет заголовки:

```http
X-User-Id: 123
X-User-Role: CLIENT
```

Сервис обязан проверять входящие заголовки у доверенных внутренних сетей и не принимать их от неавторизованного внешнего трафика.

## Auth Service

auth-service

Отвечает за идентификацию и аутентификацию пользователей.

Ответственность:

- регистрация;
- вход;
- logout;
- обновление токена;
- хранение учетных записей;
- хэширование паролей;
- выдача JWT-токенов;
- управление ролями.

Основные таблицы PostgreSQL:

```text
users
roles
user_roles
refresh_tokens
```

Роли:

```text
CLIENT
SELLER
MODERATOR
ADMIN
COURIER
```

Состав роли может расширяться по мере реализации проекта.

При входе возвращаются:

- access-токен с коротким сроком жизни;
- refresh-токен в HttpOnly cookie.

Refresh-токены должны храниться в защищенном виде с возможностью отзыва.

## Catalog Service

catalog-service

Управляет товарами маркетплейса.

Основные сущности:

```text
Book
Category
Author
Publisher
Stock
ProductStatus
```

Ответственность:

- публичный просмотр книг;
- поиск по названиям;
- фильтрация;
- пагинация;
- категории;
- остатки;
- создание товаров продавцами;
- редактирование товара;
- модерация;
- кэширование популярных запросов;
- пакетное получение товаров для корзины.

Предполагаемые endpoints:

```text
GET    /catalog/items
GET    /catalog/items/{id}
POST   /catalog/items
PUT    /catalog/items/{id}
DELETE /catalog/items/{id}
POST   /catalog/items/batch
GET    /catalog/moderation/items
PATCH  /catalog/items/{id}/status
```

Статусы товаров:

```text
DRAFT
PENDING
APPROVED
REJECTED
BLOCKED
```

Поиск может использовать PostgreSQL full-text search:

- поля `title` и `description`;
- `tsvector`;
- GIN-индекс;
- опционально `pg_trgm` для поиска с опечатками.

Redis используется для кэширования карточек товаров и результатов популярных запросов.

## Cart Service

cart-service

Управляет корзиной текущего пользователя.

Ответственность:

- получение корзины;
- добавление товара;
- увеличение или уменьшение количества;
- удаление товара;
- очистка корзины;
- получение актуальных данных из Catalog Service;
- уведомление о недоступных товарах;
- временное хранение корзины.

Предполагаемые endpoints:

```text
GET    /cart
POST   /cart/items
DELETE /cart/items/{itemId}
DELETE /cart
```

Для хранения корзины используется Redis:

```text
ключ: cart:{user_id}
значение: множество идентификаторов товаров и количество
```

Пример структуры:

```json
{
  "items": {
    "10": 2,
    "15": 1
  }
}
```

При чтении корзины Cart Service запрашивает в Catalog Service актуальную информацию пакетом.

## Схема данных

Каждый сервис владеет своими данными. Один сервис не должен напрямую изменять таблицы другого сервиса.

```text
auth-postgres
  users
  roles
  refresh_tokens

catalog-postgres
  books
  authors
  categories
  publishers
  stock
  moderation_status

cart-postgres или Redis
  user_cart
  cart_items
```

В docker-compose.yml сервисы и базы данных могут быть разделены разными контейнерами.


## Конфигурация

Конфигурация должна разделяться через переменные окружения:

- адреса баз данных;
- учетные данные базы данных;
- Redis;
- порты сервисов;
- публичный RSA-ключ;
- секреты JWT;
- URL внутренних сервисов;
- настройки тайм-аутов и circuit breaker.

Секреты не должны добавляться в Git.

## Контейнеризация

docker-compose.yml содержит инфраструктурные компоненты проекта:

- `auth-postgres`;
- `catalog-postgres`;
- `cart-postgres`;
- `redis`.

Рекомендуется также добавить сервисы приложений в compose-файл после создания JAR-файлов и Dockerfile.

Текущее имя проекта в Docker Compose можно переименовать с `map-drop` на `shu`.

## Правила расширения проекта

При добавлении нового микросервиса необходимо:

1. создать директорию в services;
2. добавить README для сервиса;
3. описать API в contracts;
4. определить собственную базу данных;
5. определить REST-взаимодействия;
6. добавить маршруты в API Gateway;
7. добавить переменные окружения в Docker Compose;
8. описать обновления в документации.
